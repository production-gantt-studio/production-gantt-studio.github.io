# Claudeへの最終実装引き継ぎプロンプト

> **使い方**：以下の「Claudeへ渡す本文」を、現行ソース一式と `docs/` ディレクトリと一緒にClaudeへ渡してください。ソースコードが仕様の最終根拠です。文章だけを見て、見た目だけの試作品を作ってはいけません。

## Claudeへ渡す本文

あなたは、既存のWebアプリ **Production Gantt Studio** を引き継ぐ主任エンジニアです。このアプリは、広告・映像・イベント・グラフィック制作のプロデューサー／PMが、案件、日程、担当、進行を分かりやすく管理するためのブラウザアプリです。

あなたの仕事は、現行アプリを**機能、画面、保存、権限、安全対策まで忠実に再実装・保守できる状態へ引き継ぐこと**です。静的な画面だけを作る、動くボタンを消す、権限や保存を省く、といった置き換えは認めません。変更前に現行ソースを読み、差分と影響を表で示してください。

## 1. 最優先の約束

1. 現行ソースが最優先の根拠です。文章と違う時は、推測せずソースとテストを確認してください。
2. 利用者が使う言葉は **管理者、編集者、閲覧者** に統一してください。
3. 最初の画面は案件一覧です。個別ガント画面を最初に出さないでください。
4. ライトモード専用です。未着手=灰、進行中・修正中=青、確認待ち=黄、完了=緑、重要・期限超過=赤を守ってください。
5. 新規案件を作れるのは、**ログインした管理者だけ**です。編集者・閲覧者・未ログインの人は作れません。
6. 標準機能では、利用者のAPIキー入力、利用者ごとの従量課金、外部サービス契約を必要としません。
7. 販売側または利用者側に、API、外部ストレージ、定期実行、従量課金などの費用が発生し得る提案は、実装前に必ず「誰に、どんな時、何の費用が発生する可能性があるか」「費用不要の代替案」を説明し、承認を得てください。
8. 現在のサイトは引き継ぎ後に非公開化する前提です。公開URLを継続利用する前提で設計・報告しないでください。

## 3. 画面と操作の必須仕様

### 3.1 案件一覧・新規案件

案件一覧には、案件名、クライアント名、登録月、開催月、進捗、タスク数、確認待ち数、日程未定数、案件を開く操作、アーカイブ操作を表示します。案件名とクライアント名で検索できます。

ログインした管理者が右上の「新規案件」を押すと、以下をすべて入力して作成します。

| 必須項目 | 内容 |
|---|---|
| 案件名 | 案件の名前 |
| クライアント名 | 相手先の名前 |
| 開催月 | カレンダーの表示終点・期間外警告に使う月 |
| 作り方 | 完全新規、動画制作、イベント制作、グラフィック制作 |

テンプレートを選んだ時は、フェーズ、担当者、タスク、依存関係、親子構造を**別IDで複製**します。複製直後のタスクは未着手・日程未定です。初期サンプルは、動画案件サンプル、イベント案件サンプル、グラフィック案件サンプルの3件だけです。実在のクライアント名をサンプルに使わないでください。

### 3.2 ガント・タスク

- フェーズ名、タスク名、担当者、状態は画面上で直接変更する。
- フェーズと親タスクは折りたためる。標準は開いた状態。
- タスクは親子構造を持てる。子タスクに進行中・修正中があれば親を進行中にし、子がすべて完了なら親を完了にする。一部が未完了なら親を自動完了にしない。
- 日程はバーの移動、バー端の変更、日付入力で変えられる。依存する後続タスクは同じ日数だけ連動する。直前の操作はUndoで戻せる。
- 日・週・月の表示を用意する。横スクロールしてもタスク列、縦スクロールしても月・日付・タスク見出しを見失わせない。
- 登録月より前の日程は許容し、警告しない。開催月を超える日程だけを期間外として警告・絞り込み対象にする。
- PDF、印刷、CSV/JSON入出力は補助操作へ置く。主導線を複雑にしない。

### 3.3 共有・招待

| 役割 | できること | できないこと |
|---|---|---|
| 管理者 | 新規案件、編集、招待、共有、設定、アーカイブ | 他人の案件を無条件に見せない |
| 編集者 | 招待済み案件のタスク・日程・担当・フェーズの変更 | 招待されていない案件の表示・変更 |
| 閲覧者 | 対象案件の確認 | 変更、設定、他案件の閲覧 |

共有URLは1案件だけを閲覧専用で表示します。共有URLと招待URLは、サーバー側で高エントロピー値を作り、DBにはハッシュだけを保存します。7日で失効し、発行者は途中で取り消せます。URLハッシュ、Base64、LocalStorageを共有データのアクセス制御に使わないでください。

## 4. 保存と「消える条件」

利用者向けには、次の説明と矛盾する動作を作らないでください。

| 状況 | 何が起きるか |
|---|---|
| ログインした管理者が作った案件 | DBに保存される。アプリが勝手に削除する仕様ではない。 |
| 管理者が案件を削除した時 | 30日間アーカイブに残る。その間は復元できる。30日後は削除対象。 |
| 共有リンクが期限切れ・取り消し | 案件は消えない。リンクだけが使えなくなる。 |
| 大きな変更前・納品前 | 設定からJSONを書き出し、会社が決めた安全な場所に保管する。 |

標準構成に、有料になり得る自動バックアップを含めません。自動バックアップを将来導入する場合だけ、費用、保存期間、復旧範囲、責任者、失敗時の扱いを先に承認してください。

## 5. セキュリティの非退行条件

次を削除・緩和しないでください。

1. 組織単位での案件・メンバー・ログのサーバー側分離。
2. 短期セッション、重要操作の再認証、同一Originでの更新制限。
3. CSP、HSTS、frame-ancestors、MIME sniffing防止、リクエスト本文上限、レート制限。
4. 共有・招待トークンのハッシュ保存、期限、取り消し、アクセス記録。
5. 認証失敗、認可拒否、権限変更、共有操作、破壊的操作のセキュリティ監査ログ。
6. 依存関係監査で高・中の脆弱性を0件に保つこと。

セキュリティに影響する変更は、変更理由、影響範囲、移行、回帰テスト、残るリスクを報告してください。詳細は `docs/security_release_gate_2026-08-20.md` を基準にします。

## 6. やさしい案内とQ&A

案件一覧の「使い方」と個別案件の「使い方」は、ログインした管理者だけが作成できること、30日アーカイブ、JSON書き出し、編集者・閲覧者の違いを説明します。

`/faq` は、小学生でも読める短いQ&Aです。少なくとも「誰が案件を作れるか」「勝手に消えるか」「削除後はどうなるか」「共有リンクが切れたらどうなるか」「編集者と閲覧者の違い」「追加費用やAPI設定が必要か」を説明します。本文を難しい言葉へ戻さないでください。

## 7. 作業手順と受入条件

最初に、次の順で作業してください。

1. 現行ソース、DBスキーマ、テスト、`docs/` を読んで、実装済み・不足・将来構想の差分表を出す。
2. 保存、権限、共有、削除、セキュリティに影響する変更を小さい単位に分け、各単位の受入条件を示す。
3. 型検査、Vitest、本番ビルド、依存関係監査を実行する。
4. デスクトップとモバイルで、案件一覧、個別案件、共有画面、使い方、Q&Aを確認する。
5. 管理者・編集者・閲覧者の実案件シナリオを確認する。

最低限、以下を合格にしてください。

| シナリオ | 合格条件 |
|---|---|
| 案件作成 | 管理者だけが、案件名・クライアント名・開催月を入力して作れる。 |
| 保存と削除 | ログイン済み案件は再ログイン後も残る。削除後30日以内は復元できる。 |
| 共有 | 共有画面から他案件・設定・編集操作へ進めない。期限切れは案件を削除しない。 |
| 権限 | 編集者は招待済み案件だけを編集でき、閲覧者は対象案件を閲覧だけできる。 |
| セキュリティ | 高・中脆弱性0件。主要HTTP保護と更新Origin拒否が有効。 |
| Q&A | `/faq` を案件一覧から開け、モバイルでも最後まで読める。 |

最後の報告では、実装内容、現行仕様との差分、テスト結果、残る制限、次の判断が必要なことを分けてください。根拠なしに「完全」「問題なし」と断定しないでください。
