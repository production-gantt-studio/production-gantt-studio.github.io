# UI/UX・エンジニアリング最終レビュー

> **対象**：Production Gantt Studio 現行版  
> **読者**：運用責任者、制作プロデューサー、PM、デザイナー、開発担当  
> **判定の目的**：限定公開の前に、使いにくさ・性能リスク・未解決のバグを分けて判断する。

## 結論

限定公開に必要な日程・担当・状態・並び替え・共有の基本操作は確認済みです。一方で、画面の情報密度と大規模案件の性能には次期改善が必要です。販売・全社展開は、実案件の権限受入と性能計測を終えるまで保留します。[1]

## デザイナー視点：次に直すべきUI/UX

| 優先 | 改善点 | 現在の観察 | 具体的な対応 | 期待する確認方法 |
|---|---|---|---|---|
| P0 | 朝の確認画面を短くする | 案件サマリー、未完了、引継ぎ、検索がガントより先に並び、長い案件ではタイムラインに到達するまでの距離が長い。 | 「今日の確認」を折りたたみ可能にし、ガントへ直接移動する入口を固定する。 | プロデューサーが3秒以内に次の担当と今日の期限を答えられるか。 |
| P0 | タスク行の編集密度を下げる | 名前、日付、日程・詳細、担当、状態、重要、並び替えが同じ行に集まり、短い画面幅で視線が散る。 | 日常操作は名前・日付・担当・状態に絞り、重要・並び替え・詳細は補助操作へ段階表示する。 | モバイル幅で担当名と日付が省略されないか。 |
| P0 | 日程編集を一段短くする | 「日程・詳細」を開けば編集できるが、日程を一日だけ直すには手数が残る。 | タスク行に開始日だけを直接変えられる小さな入力、または日付クリックで開く日程ポップオーバーを追加する。 | PMが日付変更を3操作以内で完了できるか。 |
| P1 | ガントの短いバーをさらに明確にする | 短いバーは状態名を優先するため、タスク名は左列を見直す必要がある。 | 短いバーの末尾に省略記号を置かず、左列選択時にバーだけ強調する。 | 1日タスクの名称と状態を迷わず対応付けられるか。 |
| P1 | 共有画面を確認専用の密度へ寄せる | 編集操作は隠れているが、通常画面に近い情報量が残る。 | 共有画面では「今週・確認待ち・担当者」へのショートカットを先に置き、補助パネルを閉じた状態にする。 | クライアントが日程と確認待ちだけを見つけられるか。 |
| P1 | フェーズ追加の所在を補助する | フェーズ横は「＋ タスク」に整理済みだが、フェーズ追加は設定内にある。 | フェーズ管理の入口を設定メニュー内で説明付きにし、誤操作なく見つけられるようにする。 | 初回利用者がヘルプなしでフェーズ追加に到達できるか。 |
| P2 | アクセシビリティを補う | 色は状態ルールとして統一したが、色だけで読みにくい利用者への補助がない。 | 状態バッジに形状・短いアイコン・読み上げ用ラベルを加える。 | 色を見なくても状態を区別できるか。 |

## エンジニア視点：対応済みのバグと品質状況

| 領域 | 対応状況 | 根拠 | 残る注意点 |
|---|---|---|---|
| タイムライン行同期 | 修正済み | 固定列化で発生した行ずれを解消し、タスク列とガント行を同じ表示グループで描画。 | 新しい列を増やす際は同じ行モデルへ載せる。 |
| 幅調整 | 修正済み | 横移動後も調整できるリサイズ境界を固定し、担当者欄を約158pxへ拡張。 | 極端に狭い端末では横スクロールが必要。 |
| フェーズ折りたたみ | 修正済み | 閉じた後の余白とスクロール位置を補正し、最下部行へ到達できるようにした。 | 新しいアコーディオンを追加する際はスクロール高さを再確認する。 |
| 並び替え | 修正済み | 左ハンドルを実ドラッグへ接続。同一フェーズ・同一階層だけで移動し、親は詳細タスクを伴って移動。 | モバイルは上下移動ボタンを追加すると安全性が上がる。 |
| 親子状態 | 修正済み | 詳細タスクが進行中・修正中になると、親を進行中へ更新。親背景は中立化。 | 親を自動完了にする条件は未採用。完了の責任を明示的に残す。 |
| 共有権限 | 確認済み | 閲覧共有では編集・追加・リサイズを表示しない。 | 実案件の編集者・閲覧者招待を受入確認する必要がある。 |

## パフォーマンスの現状と次の対応

| 項目 | 現在の事実 | リスク | 次の対応 |
|---|---|---|---|
| 型・ビルド・自動テスト | TypeScript型検査、本番ビルド、57件のVitestが通過。 [1] [2] | テスト通過は大規模案件での体感速度を保証しない。 | 100件、300件、500件のタスクで描画・ドラッグ・保存を計測する。 |
| 描画方式 | タイムラインは表示対象タスクをDOMへ描画する。仮想スクロールは未導入。 | 長期・大量タスク案件では描画・スクロール・ドラッグが重くなる可能性がある。 | まず描画プロファイルを取り、必要なら行の仮想化とメモ化を導入する。 |
| クライアント保存 | 日程・順序・開閉などを案件データに保存する。 | 連続ドラッグや大量編集時に保存要求が増える可能性がある。 | ドラッグ中は表示だけを更新し、確定時に保存する設計を維持・計測する。 |
| PDF | `html2canvas` と `jsPDF` は動的読み込み。 [2] | 長期ガントのPDFは端末メモリを使う。 | 26週・大量タスクのPDF生成時間と失敗率を計測する。 |
| バンドル | 本番ビルド時に大きなJSチャンク警告が残る。 [1] | 初回表示に影響する可能性がある。 | PDF、設定、共有、グラフなどを追加分割し、初回ロードを計測する。 |
| 匿名サンプル | 匿名で内蔵サンプルを開くと、認証済み案件取得APIが403を記録し、内蔵サンプルへフォールバックする。 [1] | 利用は止まらないが、不要な通信とログノイズになる。 | 匿名サンプルでは認証APIを呼ばない分岐へ改善する。 |

## リリース判定

| 配布範囲 | 判定 | 必須条件 |
|---|---|---|
| サンプルを使った限定公開 | **Ready for user review** | 利用責任者が現行画面と操作を確認する。 |
| 社内少人数パイロット | **Ready for user review** | 管理者、編集者、閲覧者の3役を1案件で確認する。 |
| 販売・全社展開 | **HOLD** | 実案件の招待・保存受入、クライアント端末の閲覧、100件超タスクの性能計測を終える。 |

## 運用責任者への次の判断

> 次に進めるべきなのは機能追加ではなく、実案件1件での受入確認です。管理者、編集者、閲覧者が同じ案件で日程・担当・順序・共有を確認した結果を、全社展開の判定材料にします。
