# 案件ごとに迷わず使うための画面遷移フロー

> **結論**：アプリの入口を「今日」ではなく**案件一覧**に固定する。利用者は、案件を選ぶか新しく作るかだけを最初に判断する。案件に入った後も、最初に見せるのは全社横断の通知ではなく、その案件の要約である。

| 項目 | 仕様方針 |
| --- | --- |
| 想定利用者 | クライアント、協力会社、社内制作メンバーを含む案件関係者 |
| 最初の画面 | **案件一覧**。Today画面は置かない。 |
| 編集 | ログイン済みの案件メンバーだけが編集できる。 |
| 閲覧 | 共有URLはログイン不要で閲覧・変更ログの確認ができる。 |
| 役割 | 編集者／閲覧者の2種類。案件ごとに変更できる。 |
| 運用の軽さ | 新規タスクはタイトルだけで作成でき、日程・担当・詳細は後から追加する。 |

## 1. 画面設計の原則

### 1.1 最初の判断は常に二つだけにする

アプリを開いた利用者に、通知、ガント、設定、メンバー管理を同時に見せない。最初に置く行動は **「案件を開く」** と **「案件を作る」** の二つだけにする。

> **案件を選べば、次に何を見ればよいかが出る。設定を理解してから使い始める必要はない。**

### 1.2 案件の中では「概要」を起点にする

ガントは重要だが、最初に常時見せる画面ではない。案件を開いた直後は、**案件概要**を表示する。概要には、その案件に限った「次の期限」「確認待ち」「日程未定」「最近の変更」を置く。利用者はそこから必要な画面へ一段で移動できる。

| 入口 | 利用者が最初に理解すること | 次の操作 |
| --- | --- | --- |
| 案件一覧 | 自分が関わる案件と状態 | 案件を開く／案件を作る |
| 案件概要 | 今回の案件で確認が必要なこと | タスク、日程、変更履歴を開く |
| タスク | 作業の分担と完了状況 | タスクを追加・編集する |
| 日程 | 依存関係を含む全体の流れ | 日程を動かす／月次へ切り替える |

## 2. 主要な画面遷移

```mermaid
flowchart TD
  A[案件一覧] -->|案件を選ぶ| B[案件概要]
  A -->|案件を作る| C[案件作成: 名前だけ入力]
  C --> D[空の案件概要]
  D -->|最初のタスクを追加| E[タスク作成: タイトルだけ入力]
  B --> F[タスク]
  B --> G[日程]
  B --> H[変更履歴]
  B --> I[共有]
  F -->|タスクを選ぶ| J[タスク詳細]
  J -->|詳細タスクを追加| K[詳細タスク]
  G -->|日程を選ぶ| J
  I --> L[共有設定]
  L --> M[共有URL: 閲覧専用]
  M --> N[外部共有ビュー]
  N --> H
