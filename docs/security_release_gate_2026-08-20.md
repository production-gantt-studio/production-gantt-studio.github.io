# 販売前セキュリティ・リリースゲート

> **判定日**：2026-08-20  
> **対象**：Production Gantt Studio  
> **判定**：**限定パイロットは可。販売開始は運用証跡の準備後に可。**

## 1. 今回の実装済みコントロール

| 分類 | 実装 | 受入証跡 |
|---|---|---|
| 依存関係 | 実行時依存を更新し、未使用の脆弱な依存連鎖を削除した。 | `pnpm audit --prod`：高・中・低・重大すべて0件。 |
| HTTP保護 | CSP、HSTS、`frame-ancestors`、MIME sniffing防止、Referrer Policy、本文上限を適用した。 | `server/_core/security.ts` と同ファイルのテスト。 |
| CSRF・Origin | 更新系APIは同一Originのみ受け付け、クロスサイト・Originなしの更新を拒否する。 | `server/_core/security.test.ts`。 |
| セッション | `HttpOnly`、`Secure`、`SameSite=Lax`のCookieを8時間で失効させ、重要操作はログイン後15分以内に限定する。 | `shared/const.ts`、`server/_core/sdk.ts`、`server/routers.ts`。 |
| 共有・招待 | URL内に案件データを入れず、高エントロピーのトークンをハッシュ化してDB保存する。共有は7日、招待は7日で失効し、取り消し可能である。 | `project_share_links`、`project_members`、`server/securityTokens.ts`。 |
| 組織分離 | 案件を組織へ属させ、案件一覧・案件取得を所有者／案件メンバー／組織メンバーの三層で検証する。 | `organizations`、`organization_members`、`projects.organizationId`。 |
| 監査 | 無効セッション、認可拒否、招待・共有の作成／利用／取消、案件作成・更新・削除を記録する。IPアドレスはHMACハッシュのみを保存する。 | `security_audit_logs`、`project_activity`。 |

## 2. リリース前の必須手順

| 段階 | 実施者 | 合格条件 |
|---|---|---|
| コード確認 | 担当エンジニア | `pnpm check`、`pnpm test`、`pnpm build` がすべて成功する。 |
| 依存監査 | 担当エンジニア | `pnpm audit --prod --json` で高・中が0件。例外は期限と責任者を記録する。 |
| 権限受入 | 管理者・編集者・閲覧者の各1名 | 別組織／未招待ユーザーが案件を読めない。閲覧者がAPI経由でも更新できない。 |
| 共有受入 | 担当エンジニア | 共有リンクで1案件だけ読める。期限切れ・取消後は読めない。トークンの平文がDB・ログ・画面に残らない。 |
| 操作受入 | 担当エンジニア | 招待、共有発行、取消、案件削除で15分を超えたセッションが拒否され、再ログイン後は成功する。 |
| 復旧演習 | セキュリティ責任者 | 下記手順で隔離環境へ復元し、案件数・招待状態・監査ログ件数を照合する。 |

## 3. バックアップと復旧

本アプリは管理DBとストレージの提供元バックアップ方針に依存する。**コードのチェックポイントはDBデータのバックアップではない。** 販売開始前に、契約するホスティング／DB提供元について、暗号化バックアップ、保持日数、地域、RPO、RTO、復元責任者を文書化する。

### 復旧目標

| 項目 | 販売開始時の目標 | 責任者 |
|---|---|---|
| RPO | 24時間以内 | セキュリティ責任者 |
| RTO | 8営業時間以内 | 運用責任者 |
| 演習頻度 | 四半期ごと、およびDB基盤変更前 | 担当エンジニア |

### 復旧演習手順

1. 事故チケットを作成し、復旧時刻、対象組織、操作担当者を記録する。
2. 本番データを直接上書きせず、隔離環境へ提供元バックアップを復元する。
3. `organizations`、`organization_members`、`projects`、`project_members`、`project_share_links`、`project_activity`、`security_audit_logs` の件数を元の時点と照合する。
4. 管理者、編集者、閲覧者、期限切れ共有リンク、取消済み共有リンクの受入シナリオを実行する。
5. 復旧に要した時間、不一致、是正内容を記録し、責任者が承認する。

## 4. インシデント対応

| 事象 | 初動 | 封じ込め | 証跡 |
|---|---|---|---|
| 共有URLの漏えい | 対象URLを特定する。 | 共有リンクを直ちに取消し、新URLを必要時だけ再発行する。 | `project.share.revoke` の監査ログ。 |
| 招待先誤り | 招待対象・役割を確認する。 | 招待を取消し、必要なら正しいアドレスで再招待する。 | `project.invite.revoke` の監査ログ。 |
| アカウント不正利用 | セッションと操作時刻を確認する。 | 該当利用者のアクセスを取り消し、再ログインを要求する。 | `auth.session.invalid`、認可拒否、案件変更ログ。 |
| 組織越境の疑い | 直ちに販売・共有を停止する。 | 影響案件・共有トークンを無効化し、復旧前に独立レビューを行う。 | 監査ログ、DBスナップショット、調査記録。 |

## 5. Claudeへの引継ぎ必須事項

Claudeは、上記の実装済みコントロールを弱めたり、LocalStorage・Base64・画面非表示だけをセキュリティ対策と見なしたりしてはならない。スキーマ変更では必ず安全なデータ移行を作り、共有・招待・組織・監査の回帰テストを追加する。販売開始を報告する前に、復旧演習の最新証跡と独立したセキュリティレビューの有無を明記する。
