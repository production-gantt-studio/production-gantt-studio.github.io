# 現行版は限定公開できるが、販売・全社展開は実案件での受入確認後に判断する

> **判定日**：2026-08-20  
> **対象版**：最終レビュー前の開発版  
> **読者**：運用責任者、制作プロデューサー、PM、デザイナー、開発担当  
> **この文書で判断すること**：サンプルを含む現行機能を限定利用へ公開してよいか。販売・全社配布を同時に行ってよいか。

## 結論

**限定公開は進められます。** 広告・イベント・グラフィックの3種類の一般名サンプル、日程変更、担当変更、タスクの順序変更、閲覧共有、折りたたみ、状態表示について、開発環境での操作確認と自動テストを完了しました。

一方で、**販売・全社配布の判断は HOLD** とします。ログイン済みの実案件で、招待・編集者・閲覧者・DB保存を含めた受入確認を、運用責任者が1案件以上で行っていないためです。これは機能の否定ではなく、利用権限と実データの運用責任をリリース前に確認するための条件です。

| 公開の種類 | 判定 | 条件 |
|---|---|---|
| サンプルを使った限定公開 | **可** | 下記の4視点レビューと自動・実操作検証を完了。 |
| 社内の少人数パイロット | **可** | 管理者1名、編集者1名、閲覧者1名で招待と編集を確認する。 |
| 販売・全社配布 | **HOLD** | 実案件での権限・招待・保存・共有の受入確認を終える。 |

## 検証の根拠

| 区分 | 実施内容 | 結果 |
|---|---|---|
| サンプル | `Sample`、`Sample Event`、`Sample Graphic`を案件一覧・案件画面で確認。実在のクライアント名は初期データから除去。 | 一般名のみで表示。 |
| 状態・親子 | 詳細タスクを追加し、状態を「進行中」へ変更。親タスクが自動で「進行中」になることを実操作で確認。 | 合格。 |
| タスク順 | 左ハンドルのドラッグ、保存後の再読み込み、親子ブロックの追従、元順への復帰を確認。 | 合格。 |
| 幅・スクロール | カレンダーを横移動後にタスク列幅をドラッグで変更。担当者選択欄は実測で約158pxを確保。フェーズを開閉後に最下部行が見えることを確認。 | 合格。 |
| 閲覧共有 | `view=shared`で、編集ボタン・追加・リサイズが出ず、予定・状態・担当者の絞り込みが読めることを確認。 | 合格。 |
| 自動検証 | 型検査、Vitest、本番ビルド。 | **23ファイル・57件のテストが通過**。 |

## 1. プロデューサー視点：案件の全体像と次の担当は確認できる

| 観点 | 確認内容 | 判定 | 根拠・制限 |
|---|---|---|---|
| 案件一覧 | 広告、イベント、グラフィックの違いを案件名と工程で判断できる。 | PASS | `Sample`、`Sample Event`、`Sample Graphic`を用意。 |
| 次の担当 | 「担当者の未完了」で、期限間近だけでなく、担当者の未完了を日程順で確認できる。 | PASS | 担当者の切替は画面内で可能。 |
| 引継ぎ | 担当変更は複数件を未確認の一覧へ残し、編集者だけが確認済みにできる。 | PASS | 3件の連続変更と個別消込を検証。 |
| 日程把握 | 日・週・月表示、固定カレンダー見出し、イベントの重要日を確認できる。 | PASS | 長い案件は月表示を推奨。 |
| 操作の意味 | フェーズ横の操作は**「＋ タスク」**と表示し、フェーズ追加ではないことを明示。 | PASS | フェーズ追加は設定内のフェーズ管理に分離。 |

> **運用上の結論**：朝の確認では「担当者の未完了」→「担当引継ぎ」→「ガント」の順で使うと、誰の作業待ちかを判断できます。

## 2. PM視点：日程変更と構造変更は制約を保って行える

| 観点 | 確認内容 | 判定 | 根拠・制限 |
|---|---|---|---|
| 日程変更 | バーの移動・延長・短縮、直接の日程編集、Undo、一括日程変更を確認。 | PASS | 依存タスクの自動日程移動は保持。通常画面の矢印は説明負荷を減らすため非表示。 |
| 親子タスク | 詳細タスクが「進行中」「修正中」になると親タスクを「進行中」へ自動更新。 | PASS | 完了率のパーセンテージは表示しない。 |
| タスク順 | 同一フェーズ・同一階層内でドラッグ並び替え。親を移動すると詳細タスクが追従。 | PASS | 別フェーズ・別階層への移動は防止。 |
| フェーズ | 標準は展開。必要なフェーズだけを折りたため、閉じた後も最下部までスクロール可能。 | PASS | フェーズ追加は設定のフェーズ管理から行う。 |
| 保存 | 開閉、日付表記、担当変更、順序変更は案件データへ保存される。 | PASS | 実案件のDB保存はパイロットで再確認が必要。 |

## 3. デザイナー視点：状態の意味を一つにし、情報の優先順位を保つ

| 観点 | 確認内容 | 判定 | 根拠・制限 |
|---|---|---|---|
| 色の意味 | 未着手=灰、進行中・修正中=青、確認待ち=黄、完了=緑、重要=赤をタスク行・ガントバー・概要で統一。 | PASS | 重要日は赤い縦線とラベルで表示。 |
| バーの可読性 | バー面は状態色、文字は白。長いバーはタスク名、短いバーは状態名を中央に表示。 | PASS | 文字数が長いタスク名は短いバーに収まらないため、状態名を優先する。 |
| 親タスク | 親タスクの背景色による強調を廃止。状態はバッジとガントバーの色だけで判断。 | PASS | 詳細タスク数は補助情報として残す。 |
| 日程導線 | タスク行に「日程・詳細」を置き、詳細画面の最上部へ開始日・終了日・日程未定を集約。 | PASS | より速い日付直接編集は次期候補。 |
| モバイル | 案件サマリー、担当者の未完了、引継ぎ、タスク列を確認。ガントは横スクロールで閲覧。 | PASS | 横幅が狭い端末ではカレンダー全体を同時には読めない。 |

## 4. エンジニア視点：主要な状態遷移と画面回帰は確認した

| 観点 | 確認内容 | 判定 | 根拠・制限 |
|---|---|---|---|
| 静的品質 | TypeScript型検査と本番ビルドを実行。 | PASS | ビルド時の大きなJSチャンク警告は残るが、機能エラーではない。 |
| 自動テスト | アクセス制御、アラート、日付、PDF範囲、折りたたみ、状態、引継ぎ、並び替え、サンプル移行を検証。 | PASS | 23ファイル・57件。 |
| 実操作 | フェーズ内タスク追加、親子状態同期、横移動後の幅調整、担当者欄、フェーズ折りたたみ後の最下部到達をブラウザで確認。 | PASS | 隔離したブラウザで確認。 |
| 閲覧権限 | 共有モードで編集操作・追加操作・リサイズ操作が表示されない。 | PASS | 画面確認済み。 |
| ログ | 匿名でサンプル案件URLを開いた時、認証済み案件取得APIが403を返す記録がある。画面はローカルの内蔵サンプルへフォールバックする。 | **要観察** | 利用者の画面を止めないが、将来は匿名サンプルに対するAPI要求を省く。 |

## 公開前に運用責任者が行う最後の確認

1. 管理者が実案件を1件作成する。
2. 編集者を1名、閲覧者を1名招待する。
3. 編集者が日程・担当・タスク順を変更し、閲覧者が変更できないことを確認する。
4. 閲覧URLをクライアントまたは協力会社の担当者に送り、モバイルで日程と担当が読めるかを確認する。

この4点が終われば、販売・全社配布の判断材料がそろいます。
