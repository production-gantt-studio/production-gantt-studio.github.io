# 現行ガントは「期限確認」には使えるが、日々の進行・引継ぎ・自分の仕事を支える画面ではない

**対象読者：** 制作プロデューサー、PM、導入判断者  
**文書の状態：** **Draft / user review**。現行実装の点検結果と、実装前に合意すべき改善方針を示す。  
**対象版：** Production Gantt Studio `cbc6ba61`。通常画面・閲覧共有画面・モバイル画面、日表示・週表示を点検した。

> 結論は明確です。現行画面は、期限が迫った仕事を拾う用途には使えます。しかし、プロデューサーが日程を先へ動かしながら「これはどのフェーズの何の仕事か」を読み続けること、複数人へ仕事を渡して誰がまだ確認していないかを追うこと、自分または特定担当者の未完了タスクをまとめて見ることには、まだ耐えません。

## 1. 今回の点検範囲と、制作現場で問うべき判断

このレビューでは、デザインの好みではなく、制作進行で頻発する次の4場面を基準にしました。

| 場面 | 利用者が判断したいこと | 現行の判定 |
|---|---|---|
| 朝の確認 | 今日だけでなく、**自分／担当者ごとの未完了案件**は何か | **不合格**。期限間近のアラートには寄れるが、未完了一覧の入口がない。 |
| 日程を先へ送る | 先のバーを見ても、**どのフェーズ・どのタスクか**を取り違えないか | **不合格**。横スクロールで左のフェーズ・タスク列も画面外へ出る。 |
| 担当を渡す | 誰が誰へ何を渡したか、受け手が確認したか | **不合格**。画面上の注意表示は1件だけで、短時間で消える。 |
| クライアント確認 | 編集せず、進行・確認待ち・次の窓口を追えるか | **条件付き合格**。閲覧制限は守られているが、自分に関係する未完了タスクを探しにくい。 |

この表の「不合格」は、機能がないという意味ではありません。**必要な情報へたどり着く前に、利用者が記憶・目視・操作を余分に求められる**状態を意味します。制作進行では、撮影・修正・クライアント確認が重なる日に、この余分な負荷が見落としにつながります。

## 2. ご指摘の3点は、いずれも画面構造の問題である

### 2-1. カレンダーを移動すると、フェーズとタスクが消える

**事実：** 現行の横スクロール領域には、タスク列とカレンダー列が同じレイアウト要素として入っています。そのため、カレンダーを右へ送ると、フェーズ名・タスク名も同時に左へ流れます。[1] [3]

これは単なる「見た目の不便」ではありません。8月の「撮影準備」を確認して9月の「初稿」「MA」へ移動したとき、バーだけが残ると、利用者は一覧を記憶するか、左へ戻るしかありません。長期案件ほど、バーの色と位置だけでは工程を識別できなくなります。

**採るべき方針：** タスク列を固定レールにします。フェーズ見出し・タスク名・担当・状態は左に残し、右側のカレンダーだけを横移動させます。タスク列の幅調整は維持し、各行の高さはカレンダー側と常に同期させます。

> 受入条件：6か月先まで横移動しても、表示中のすべてのバーについて「フェーズ名」「タスク名」「担当」「状態」を左列で確認できること。日・週・月表示、通常・共有・モバイルで同じ原則を守ること。

### 2-2. 担当変更がすぐ消え、複数件を追えない

**事実：** 現行の担当変更表示は、単一の画面状態として持たれ、8秒後に消えます。次の変更をすると前の表示は置き換わります。[1]

この仕様は「変更できた」ことを操作した人に知らせるだけです。進行管理で必要なのは、**渡した仕事が残っているか、受け手が確認したか、期限が近いか**です。特に修正戻しで3件、5件と担当を振り直すとき、最後の1件だけ見えても引継ぎにはなりません。

**採るべき方針：** 一時通知を延長するのではなく、案件内に**引継ぎ一覧**を設けます。担当変更ごとに「変更者／変更前／変更後／タスク／期限／変更時刻」を追加し、未確認は残します。担当者本人または管理者が「確認済み」にして初めて一覧から外す運用にします。変更ログは監査用として残し、引継ぎ一覧は日常の未処理箱として扱います。

> 受入条件：3件連続で担当を変えた場合、3件とも引継ぎ一覧に残ること。ゲストを含め、担当者名を選ぶだけで自分向けの未確認引継ぎを読めること。確認済み操作はタスクの状態・日程を変更しないこと。

### 2-3. 期限間近以外の自分の割当を知りたい

**事実：** 現行のアラートは、未担当、期限超過、7日以内の期限接近、重要タスクを抽出する設計です。期限が先の通常タスクは、担当者タブを選んでも表示対象になりません。[2]

このため「自分は来週から何を始めるのか」「外部スタッフに渡した素材準備は全部そろっているか」という日常の問いに答えられません。アラートは例外検知には向きますが、担当一覧の代わりにはなりません。

**採るべき方針：** アラートとは別に、常設の**自分の担当**ビューを置きます。ログイン済みの編集者は自分を初期選択し、ゲストは担当者名を選びます。表示対象は完了以外の全タスクで、日程順に並べます。上部で「今日」「今週」「すべて」「日程未定」を切り替えられるようにします。

> 受入条件：期限が1か月先の未完了タスクも、担当者を選ぶだけで表示されること。日程未定は最後に独立表示し、期限アラートと混ぜないこと。閲覧者にも同じ確認機能を提供し、編集操作は出さないこと。

## 3. 追加で見つかった、導入を阻む問題

| 優先度 | 観察した問題 | なぜ制作現場で危険か | 改善方針 |
|---|---|---|---|
| **P0** | タイムラインを横へ送ると、バーの文脈が消える。 | 工程・担当の誤認は、撮影準備や納品前の漏れにつながる。 | タスク列・フェーズ列を固定し、カレンダーだけを横スクロールする。 |
| **P0** | 担当変更は一時通知で終わり、確認責任が残らない。 | 多件数の振り分け後に、誰が受け取ったか追えない。 | 複数件を残せる引継ぎ一覧と確認済みを追加する。 |
| **P0** | 担当者別表示が「期限アラート」に限られる。 | 期限前の準備・先回りの作業が見えず、担当者は自分で記憶する必要がある。 | 全未完了を見せる「自分の担当」を独立させる。 |
| **P1** | 画面上部の進捗・アラート・操作が縦に積まれ、モバイルではガントへ到達するまで長い。 | 朝の30秒確認で、タイムラインより上部情報を読む時間が長くなる。 | モバイルでは「自分の担当」を最上部に置き、進捗とアラートは折りたたみ可能にする。 |
| **P1** | 状態色は改善されたが、短いバーではタスク名より状態ラベルが優先される。 | 状態は読めても、作業内容は左列へ視線を戻す必要がある。 | 左列固定後に、短いバーの役割を「状態」、左列の役割を「作業名」と明確に分ける。 |
| **P2** | 共有画面にも管理者向けの情報密度が一部残る。 | クライアントが見るべき判断材料と、制作側の運用情報が混ざる。 | 共有画面は「進捗・次の確認・重要日・担当別未完了」へ絞る。 |

## 4. 実装の順序：通知を増やす前に、見る場所を固定する

### 第1段階：毎日使う3画面を先に成立させる

最初に実装すべきは、次の3つです。

| 画面 | 表示するもの | 表示しないもの |
|---|---|---|
| **ガント** | 固定タスク列、横移動するカレンダー、状態バー、重要日 | 担当変更の一時通知だけで終わる表示 |
| **自分の担当** | 担当者、未完了タスク、期限、状態、フェーズ、日程未定 | 他人の緊急アラートを優先した一覧 |
| **引継ぎ** | 未確認の担当変更、変更者、期限、確認済み操作 | 8秒で消える単一メッセージ |

ここで重要なのは、通知・色・新しいカードを足すことではありません。**「どこを見れば、誰が何を次にするかが分かるか」を固定すること**です。

### 第2段階：役割に応じて初期画面を変える

編集者が開いたときは自分の担当を初期表示し、管理者は全体ガントを初期表示します。閲覧者は、共有された案件の進捗と自分が選んだ担当者のタスクを確認できるようにします。この差は権限の差ではなく、確認したい最初の問いの差です。

### 第3段階：実利用シナリオでしか公開しない

以下の操作を、通常・共有・モバイルで実演できるまで公開しません。

| シナリオ | 合格条件 |
|---|---|
| 6か月後へカレンダーを送る | 左列のフェーズ・タスク・担当が残り、対象バーを特定できる。 |
| 3件の担当を連続変更する | 3件が引継ぎ一覧に残り、1件ずつ確認済みにできる。 |
| 担当者「山本」を選ぶ | 期限が先の未完了も含め、日程順にすべて表示される。 |
| クライアント共有を開く | 他案件・編集操作は出ず、必要な進捗と担当状況だけを確認できる。 |
| 375px幅で開く | 自分の担当へ1操作以内で到達し、横スクロール後もタスク名を失わない。 |

## 5. 今回は採らない方がよい対応

| 対応案 | 判定 | 理由 |
|---|---|---|
| 担当変更通知を8秒から30秒へ延ばす | **採らない** | 消える・1件だけという構造は変わらない。 |
| アラートの担当者タブに全タスクを足す | **採用しない** | 例外検知と担当一覧の目的が混ざり、緊急度が読めなくなる。 |
| バーの文字をさらに小さくしてタスク名も状態も詰め込む | **採らない** | 長期案件では読めず、フェーズ・タスク列の固定という根本を避けるだけになる。 |
| メール通知を増やす | **後回し** | ゲスト参加者を含む現行の運用では、画面内の未確認箱を先に成立させるべきである。 |

## 6. 導入判断者への結論

現状のアプリは、ガントを編集できるところまで到達しています。しかし、制作チームが継続利用するために必要な「進行の座標軸」がまだありません。カレンダーを動かしても作業名が残ること、仕事を渡したら確認されるまで残ること、担当者が期限に関係なく自分の未完了を見られること。この3点をP0として直すべきです。

この順番なら、日程変更・担当変更・共有という現場の基本動作を、追加の外部サービスなしで支えられます。逆に、この3点を後回しにしてカードや通知だけを増やすと、情報量は増えても「次に誰が何をするか」は分かりません。
