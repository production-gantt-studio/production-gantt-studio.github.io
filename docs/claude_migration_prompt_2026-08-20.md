# Claudeへの移行プロンプト — Production Gantt Studio

> **使い方**：この文書の「Claudeへ渡す本文」を、そのままClaude CodeまたはClaudeの開発環境へ貼り付けてください。あわせて、現行ソース一式を渡してください。ソースが渡せない場合は、本文内の仕様を基準に再実装しますが、UIの細部や既存データ移行は現行ソースを基準にしてください。

## Claudeへ渡す本文

あなたは、既存のWebアプリケーション **Production Gantt Studio** を保守・再実装する主任エンジニアです。対象は広告・映像・イベント・グラフィック制作のプロデューサー／PM向けの、軽量なガントチャートWebアプリです。

この依頼の最優先事項は、**現行アプリの情報、操作、権限、データ分離、保存挙動を失わずに引き継ぐこと**です。画面を静的なモックへ置き換えたり、動く機能を見せかけのボタンに変更したりしてはいけません。仕様に不明点があれば、まず現行ソースを確認し、推測で機能を減らさないでください。

## 1. 成果物と作業原則

### 1.1 成果物

次の状態を作ってください。

1. 現行仕様を満たす、起動可能なソースコード。
2. ローカル起動・本番ビルド・テストの手順書。
3. 現行データを読み込める移行処理、または移行不能な場合はその理由と安全な移行手順。
4. 実装した機能・未実装の将来構想・運用上の注意を分けた `README` または `docs/handoff.md`。
5. 主要仕様を網羅する自動テストと、手動受入テスト表。

### 1.2 作業原則

- 現行ソース一式を**真実の基準**とする。画面の見た目だけで再現しない。
- 保存、閲覧権限、案件分離、アーカイブ、共有URL、依存関係の連動は、見た目より優先して保持する。
- 外部の有料APIを前提にしない。メール送信や認証を追加する場合は、無料枠・自前SMTP・既存認証基盤など、導入費用と運用責任を明示する。
- 利用者のAPIキー入力、利用者ごとの従量課金、外部サービス契約を標準機能の前提にしない。販売側または利用者側に費用が発生し得るAPI、ストレージ、定期実行、外部サービスを提案・実装する前に、負担者、発生条件、代替案を説明して承認を得る。
- 標準のデータ保護は、認証済みDB保存、30日間アーカイブ、案件責任者によるJSON書き出しである。自動バックアップは、費用、保存期間、復旧範囲を販売責任者が承認した場合だけ導入する。`docs/data_retention_and_recovery_guide_2026-08-20.md` を参照すること。
- ユーザーが指定していない機能を、便利そうという理由だけで追加しない。特に、請求、決済、分析、AI自動生成、過度に複雑な権限は対象外とする。
- データを消す処理、権限を緩める処理、共有範囲を広げる処理は、必ず確認画面とテストを用意する。
- 各変更後に、型検査、テスト、本番ビルドを実行する。UI変更ではデスクトップとモバイルの表示も確認する。

### 現行技術構成

現行版は、React 19、TypeScript、Vite、Express、tRPC、Drizzle ORM、MySQL、Tailwind CSS、shadcn/ui、Wouter、Vitestで構成されています。認証は現在のホスティング環境のOAuthを利用しています。PDFは `html2canvas` と `jsPDF` を使います。データは、認証済み案件ではDB、未認証・フォールバックではLocalStorageに保持します。

技術を置き換えても構いません。ただし、置換前に「どの機能をどのデータモデル・認証方法・保存方法で担保するか」を表で示し、以下の動作を失わないでください。

## 3. 利用者と権限

アプリ内で使う呼称は、**管理者、編集者、閲覧者**だけに統一します。「編集できる人」「見るだけの人」など、役割名を曖昧にする表記は使いません。

| 役割 | 現行の操作範囲 | 必須の制約 |
|---|---|---|
| 管理者 | 新規案件作成、案件編集、招待、共有、設定、アーカイブ | 他人の案件を無条件に見せない。新規案件の作成は管理者のみ。 |
| 編集者 | 招待済み案件のタスク、日程、フェーズ、担当、状態、共有・招待を操作 | 招待されていない案件は一覧にも表示しない。 |
| 閲覧者 | 招待URLまたは共有URLから、対象案件の内容を確認 | 追加、編集、削除、リサイズ、設定、他案件一覧を表示しない。 |

### 現行の招待フロー

- 編集者は、招待されたメールアドレスでログインして参加する。
- 閲覧者は、招待リンクからログイン不要で対象案件を確認できる。
- 招待には `editor` と `viewer` の区別、招待中・参加済み・取り消し済みの状態がある。トークンは高エントロピー値をハッシュ化してDB保存し、7日で失効する。
- 招待取り消し後は、該当のメンバーを編集可能な状態に残さない。

### 共有URLの原則

- 共有URLは閲覧専用で、対象の**1案件だけ**を表示する。
- 共有画面に案件一覧、別案件、編集ボタン、設定、タスク追加、並び替え、サイズ変更を表示しない。
- 共有URLはサーバー側の高エントロピートークンで発行し、DBにはSHA-256ハッシュだけを保存する。共有リンクは7日で失効し、発行者は失効前でも取消できる。
- Base64・URLハッシュ・LocalStorageを、共有データの保存やアクセス制御に使わない。共有トークンの平文をDB、監査ログ、画面へ保存・表示しない。

### 販売向けセキュリティの非退行条件

`docs/commercial_security_baseline_for_business_tools.md` と `docs/security_release_gate_2026-08-20.md` を必須仕様として扱う。再実装では、8時間セッション、重要操作の15分再認証、同一Origin更新制限、CSP/HSTS、レート制限、組織メンバーシップを含むサーバー側認可、ハッシュ化・期限付き・取消可能な共有と招待、監査ログを保持する。これらを削除・緩和する変更は、理由、影響、移行、回帰テスト、セキュリティ責任者承認なしに行ってはならない。

## 4. 案件一覧と新規案件作成

### 4.1 案件一覧

案件一覧はアプリの入口です。個別ガント画面を最初に出さないでください。各案件カードには、少なくとも次を出します。

- 案件名
- クライアント名
- 登録月と開催月
- 進捗概要
- タスク数、確認待ち数、日程未定数
- 案件を開く導線
- アーカイブ導線

検索は案件名・クライアント名を対象にします。削除は即時消去ではなく、30日間のアーカイブへ移します。アーカイブ内では復元でき、期限を過ぎたものは端末側保存から削除されます。

### 4.2 新規案件の必須入力

新規案件は管理者が作成します。作成前に以下を**必須入力**にしてください。

| 項目 | 入力形式 | 用途 |
|---|---|---|
| 案件名 | テキスト | 案件一覧・個別画面の名称 |
| クライアント名 | テキスト | 案件識別・一覧検索 |
| 開催月 | `YYYY-MM` の月入力 | カレンダーの表示終点・期間外警告 |
| 作り方 | 4択 | 初期タスクとフェーズの有無 |

作り方は次の4つです。

| 選択肢 | 初期状態 |
|---|---|
| 完全新規 | タスク・フェーズ・担当者なしの空案件 |
| 動画制作 | 企画、撮影、編集、納品の標準工程 |
| イベント制作 | 企画、設営、本番、事後対応の標準工程 |
| グラフィック制作 | 方向性、デザイン、入稿、納品の標準工程 |

テンプレートを選んだ場合、フェーズ、担当者、タスク、依存関係、親子関係を**新しいIDに複製**します。複製したタスクはすべて `未着手` かつ `日程未定` とし、過去のサンプル案件の日付・状態・編集履歴を引き継ぎません。テンプレートの重要フラグは必要に応じて引き継げますが、重要日そのものは案件ごとに確認する必要があります。

### 4.3 サンプル案件

初期サンプルは次の3件だけです。

1. `動画案件サンプル`
2. `イベント案件サンプル`
3. `グラフィック案件サンプル`

実在のクライアント名をサンプルに使わないでください。過去の `Sample`、`Sample Event`、`Sample Graphic`、実在名を含む旧サンプルは、新名称へ正規化します。タスク2件・クライアント未設定の不要な `Sample` は削除対象です。

## 5. ガント・タスク・フェーズの必須仕様

### 5.1 基本構造

- フェーズは編集、追加、削除、並び替えが可能。標準は展開状態。
- タスクはフェーズ内に作成し、名前、担当者、状態を行内で直接変更できる。
- タスクには詳細タスク（親子階層）を追加できる。
- フェーズと親タスクは折りたたみ可能。折りたたみ状態は案件データに保存する。
- 同一フェーズ・同一階層内ではドラッグで順序変更できる。親タスクを動かすと、直属の詳細タスクも同じブロックとして追従する。
- 異なるフェーズや異なる階層へドラッグして、構造を壊すことはできない。

### 5.2 タスク状態と色

以下の意味をすべての画面、バッジ、ガントバー、概要で統一します。

| 状態・用途 | 色 |
|---|---|
| 未着手 | 灰 |
| 進行中・修正中 | 青 |
| クライアント確認中 | 黄 |
| 完了 | 緑 |
| 重要・期限超過・重要日 | 赤 |

ライトモード専用です。ダークモードを追加しないでください。ガントバーは状態色で塗り、文字は白で読みやすくします。長いバーはタスク名を優先し、短いバーは状態名を中央表示します。重要日は、はっきりした赤白の縦線・ラベルで見分けられる必要があります。

### 5.3 親子タスクの状態同期

親子状態には次の規則があります。

- 子タスクのいずれかが `進行中` または `修正中` のとき、親タスクを `進行中` にする。
- 子タスクが**すべて完了**したとき、親タスクを `完了` にする。
- 子タスクに未完了が残る場合、親タスクを自動完了にしない。
- 親タスク自体に子タスクがない場合、この自動規則を適用しない。
- 親の完了率パーセンテージは通常画面に表示しない。

### 5.4 日程変更と依存関係

- タスクは、ガントバーのドラッグ移動、開始端・終了端のリサイズ、日付編集で変更できる。
- 日単位でスナップする。日／週／月の表示を切り替えられる。
- 前段タスクを変更すると、依存関係でつながった後続タスクを同じ日数だけ自動で動かす。
- 複数タスクを選択し、一括で移動・期間変更できる。
- 直前のタスク日程操作はUndoで戻せる。
- 日程が未定のタスクを作成できる。

### 5.5 期間の規則

- カレンダーは**登録月から開催月まで**を表示する。
- 登録月より前の日付のタスクは許容し、警告しない。
- 開催月を超える日付のタスクだけを「期間外」として警告・絞り込み対象にする。
- 開催月を変更したときも、開催月超過のタスクを警告する。

## 6. アラート、担当、日付、変更履歴

### アラートと担当

- 期限超過、期限接近、未担当を画面上でアラート表示する。メール通知は不要。
- アラートには担当者名を表示する。
- 担当者タブで、ログイン状態に依存せず担当者ごとのアラートと未完了タスクを確認できる。
- 担当者変更は一時的な通知で終わらせず、未確認の引継ぎ一覧へ複数件保存する。編集者は各引継ぎを確認済みにできる。

### 日付表示

- 案件ごとに、`月日`、`月日＋曜日`、`年・月・日` を選べる。
- 縦スクロールしても、月・日付・タスク列の見出しを固定する。
- 横スクロールしても、フェーズ・タスク・担当・状態の左列は固定する。
- タスク列の横幅は調整可能で、横移動後も調整操作が使える。

### 変更履歴

- 認証済み案件では、案件作成、案件更新、招待作成、招待受諾、招待取消をDBへ記録する。
- 変更ログは案件ごとに時系列で確認できる。
- 閲覧者に変更ログをどこまで見せるかは、現行ソースの実装に合わせる。将来の仕様を現行の実装済み機能として扱わない。

## 7. 出力、入出力、共有

- PDF出力は、全体、フェーズ、選択タスクの範囲を選べる。長期スケジュールはA4向けのレイアウトで出力する。
- 印刷操作とUndoは、上部の主操作ではなく「その他」内の補助操作にまとめる。
- CSV／JSONのインポート・エクスポートは設定内に置き、案件画面の主導線には置かない。
- 閲覧共有URLは案件をまたいで情報を出さない。

## 8. 画面設計と文章

このアプリは、一般的な多機能SaaSではなく、制作現場で毎朝「どの案件で、誰が、何をするか」を確認するための道具です。画面を増やしすぎず、フェーズ名、タスク名、担当者、状態は可能な限りその場で変更できるようにしてください。

### 必ず守るUI原則

- 最初の画面は案件一覧。
- 新規案件の入口は右上に集約する。
- 「ゼロスタート」ではなく「新規案件」と表記する。
- 上部操作は最小限に保つ。PDF、印刷、Undo、一括選択は補助操作へまとめる。
- 通常時のアラートは1行要約に折りたたみ、期限超過・期限接近・未担当がある時だけ展開する。
- タスクを選んだ時の詳細入口は明確にし、日程入力を迷わせない。
- モバイルでは横スクロールを許容するが、重要なタスク情報と操作導線を潰さない。
- 「使い方」は案件一覧と個別案件の両方から開ける。内容は、作成、テンプレート、日程、依存連動、アラート、共有、権限、変更履歴、アーカイブの現行仕様に一致させる。

## 9. データモデルと保存要件

### 現行DBモデル

| テーブル | 要点 |
|---|---|
| `users` | OAuth識別子、氏名、メール、`admin`／`user` ロール |
| `projects` | `publicId`、所有者、案件名、クライアント名、開催月、案件JSON、日時 |
| `project_members` | 案件、招待メール、`editor`／`viewer`、招待状態、招待トークン |
| `project_activity` | 案件、操作ユーザー、操作種別、詳細、日時 |

案件JSONには、少なくともタスク、フェーズ、担当者、重要日、折りたたみ状態、担当引継ぎ、登録月、開催月、日付表記設定、更新日時を保持します。

### 保存の注意

- 認証済みの案件はDBが正本。LocalStorageはオフライン／フォールバック用途として扱う。
- 既存案件を読んだ時、古いサンプル名や不足フィールドを安全に補完する。
- タスク、フェーズ、設定、順序、開閉状態、引継ぎの変更を保存する。
- 破壊的なDB変更を行う前に、バックアップまたは移行手順を用意する。

## 10. 将来構想：実装済みと混同しないこと

以下は、**現行の完成済み機能ではなく、販売・社内配布へ進むための将来設計**です。勝手に現行版へ混ぜず、別フェーズとして扱ってください。

1. メールのマジックリンクによるパスワード不要ログイン。
2. 組織（テナント）ごとの完全なデータ隔離。
3. 組織管理者、ライセンス、編集者上限、契約状態。
4. 共有リンクの有効期限、停止、サーバー側トークン化。
5. 組織単位の変更ログ、監査、ストレージ上限、請求。

現行版は少人数パイロットまでが検証済みです。販売・全社展開は、実案件1件で「管理者1名、編集者1名、閲覧者1名」の招待、編集、保存、共有、モバイル閲覧を受け入れ確認してから判断してください。

## 11. 必須テストと受入条件

実装後は、少なくとも以下を満たしてください。

### 自動テスト

1. 型検査が通る。
2. 単体テストで、依存関係の日程連動、親子状態同期、アラート、期間外判定、日付表示、アコーディオン、並び替え、テンプレート複製、アクセス制御を検証する。
3. 本番ビルドが通る。

### 手動受入テスト

| シナリオ | 合格条件 |
|---|---|
| 完全新規作成 | 案件名・クライアント名・開催月なしでは作成できず、入力後は空の案件が作成される。 |
| テンプレート作成 | 動画・イベント・グラフィックの各テンプレートで、新しいIDのフェーズ・担当・タスクが作成され、タスクは未着手・日程未定。 |
| 日程連動 | 先行タスクを動かすと後続依存タスクが同じ日数だけ動き、Undoで戻せる。 |
| 親子状態 | 子タスクが全完了なら親が完了。一部未完了なら親は自動完了しない。 |
| 期間警告 | 登録月前は警告なし、開催月超過だけ警告・絞り込み対象。 |
| 権限 | 編集者は招待済み案件を編集でき、閲覧者は対象案件だけを編集不能で見られる。 |
| 共有 | 共有URLで他案件、設定、編集操作が見えない。 |
| アーカイブ | 削除後30日以内に復元できる。 |
| レスポンシブ | デスクトップとモバイルで、案件一覧、固定タスク列、マニュアル、ガントの主要情報が崩れない。 |

### 完了報告の形式

完了報告では、次を明示してください。

1. 実装したこと。
2. 現行仕様と異なる点があれば、その理由と影響。
3. 実行した型検査、テスト、本番ビルドの結果。
4. 未実装の将来構想と、現在の制限。
5. 実案件パイロットで確認すべき事項。

「完全」「問題なし」などの断定は、受入テストの証跡なしに使わないでください。

質問が必要な時は、選択肢を並べるだけでなく、**何が変わるか、どのリスクを避ける質問か**を一文で添えてください。
