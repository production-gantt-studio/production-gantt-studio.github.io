# Agency OS基準の照合は保留、販売向けセキュリティ適合はHOLD

> **2026-08-20 改訂**：本資料の旧評価に含まれていた、1年セッション、Base64共有、共有取消不能、組織スコープなし、HTTP保護・レート制限なし、実行時依存の高・中脆弱性という指摘は、今回の改修で解消した。現在の実装・受入条件は [販売前セキュリティ・リリースゲート](./security_release_gate_2026-08-20.md) を正とする。

> **改訂後の結論**：Agency OSの正式な要件書が未提供のため、Agency OS適合の断定は引き続きしない。ただし、公開のOWASP ASVSとNIST SSDFを基準とする内部ベースラインに対して、アプリケーション側のP0・P1実装は完了した。販売開始は、提供元バックアップ契約の確認、隔離環境での復旧演習、独立したセキュリティレビューを証跡化した後に判断する。

> **旧結論（改訂前の監査時点）**：現行のProduction Gantt Studioは、OAuthの状態検証、署名済みセッション、案件単位のサーバー側認可などの基礎制御を実装している。一方で、公開されたAgency OSの正式なセキュリティ基準を確認できなかったため、「Agency OS基準を満たす」とは判定できない。さらに、実行時依存関係監査で高重大度17件・中重大度47件が検出され、共有URL・セッション・CSRF・レート制限・組織分離・運用監視にも販売前に解消すべき不足がある。このため、**販売・全社展開の適合判定はHOLD**とする。

## 1. 評価の範囲と判断方法

本評価は、現行ソース、DBスキーマ、認証・認可処理、共有実装、依存関係監査、公開されたOWASP・NIST資料を基準にした設計レビューである。侵入テスト、クラウド基盤設定監査、ソースの第三者監査、実顧客環境での運用監査は含まない。そのため、脆弱性が存在しないことを保証するものではない。

| 評価対象 | 確認した根拠 | 評価に含まれないもの |
|---|---|---|
| アプリ認証・認可 | OAuthコールバック、セッション署名、tRPCガード、案件アクセスDBクエリ | OAuth提供者・ホスティング基盤の設定監査 |
| 案件分離・共有 | 案件取得、招待、共有URL、閲覧画面 | 実顧客データでの越境試験 |
| 依存関係 | `pnpm audit --prod` | 将来公開される脆弱性、OS・コンテナ監査 |
| 開発プロセス | 型検査、Vitest、本番ビルド、現行のレビュー資料 | 独立第三者によるペネトレーションテスト |

OWASP ASVSは、Webアプリケーションの技術的セキュリティ制御を検証し、調達要件にも使える公開基準である。[1] NIST SSDFは、組織準備、ソフトウェア保護、安全な開発、脆弱性対応の4群で安全な開発プロセスを整理している。[2] 本資料では、この二つを販売向け基準の骨格に使う。

## 2. Agency OSとの照合可否

### 判定：**HOLD（基準原本が未確認）**

「Agency OS」という名称について、公開Web上で本アプリへ適用できる正式なセキュリティコントロール一覧、認証要件、監査証跡、合格判定を確認できなかった。そのため、Agency OSが社内基準、既存プロダクト、顧客の調達要件、または別サービスを指す場合、**基準原本がない状態で適合を表明してはいけない**。

次のいずれかを受領した時点で、本資料のコントロールIDへ1対1で再照合する。

1. Agency OSのセキュリティ要件書、チェックリスト、監査報告書。
2. 必須認証・SLA・データ保持・ログ・インシデント対応の要件。
3. 取引先が求めるSOC 2、ISO 27001、ISMS、個人情報保護、データ所在地などの調達条件。

> したがって、現在言える正確な結論は「**Agency OSとの適合は未判定**」であり、「満たしている」でも「満たしていない」でもない。販売向けの公開基準に照らした現行版の判定は、次節以降のとおりHOLDである。

## 3. 現行実装で確認できた制御

| 領域 | 確認済みの実装 | 評価 |
|---|---|---|
| OAuth状態検証 | ログイン開始時にランダムnonceをCookieと`state`へ保持し、コールバックで一致しなければ拒否する。 | 基礎制御あり。 |
| セッション | サーバーはHS256署名済みJWTを検証し、`HttpOnly`・`Secure`属性を付けたCookieを使用する。 | 基礎制御あり。ただし有効期間は1年。 |
| API認可 | 保護対象のtRPC手続きはログインを要求し、案件取得・更新では所有者または有効な案件メンバーをサーバー側で照合する。 | 案件単位の認可は実装済み。 |
| 役割 | 管理者、編集者、閲覧者を区別し、閲覧者には更新権限を与えない。 | サーバー側の編集拒否を含む。 |
| 招待 | 編集者はメール一致とログインを要求し、閲覧者は招待トークンで対象案件を開く。 | トークンの期限・ハッシュ・利用回数制御は未実装。 |
| DBアクセス | Drizzleのクエリで所有者または有効メンバーを条件にして案件を取得する。 | URLの案件IDだけを信頼する設計ではない。 |
| 入力 | API入力はZodで長さ・形式を制約し、Reactの通常描画は文字列をエスケープする。 | 基礎的な入力処理あり。 |
| 変更ログ | 案件作成・更新・招待・招待受諾・招待取消をDBへ記録する。 | 最低限の追跡性あり。 |

## 4. 販売前に解消すべき不足

以下は、既存機能の否定ではなく、販売対象のSaaSとして必要になる安全境界と運用証跡である。

| 優先度 | 不足・リスク | 現行の根拠 | 販売前に必要な対応 |
|---|---|---|---|
| **P0** | 実行時依存関係に既知脆弱性が残る | 2026-08-20の`pnpm audit --prod`で高17件、中47件、低8件を検出。 | 高・中重大度を原則0件にする。直接・間接依存を更新し、更新不能な例外は影響、緩和策、期限、承認者を記録する。 |
| **P0** | CSRF対策がOAuth開始以外で明示されていない | セッションCookieが`SameSite=None`で、更新APIに独立したCSRFトークン検証がない。 | SameSite方針を見直し、クロスサイト更新が必要ならCSRFトークンまたはOrigin／Referer検証を導入し、更新操作をテストする。 |
| **P0** | HTTP保護ヘッダー・レート制限が未実装 | サーバーはJSON／URLエンコードのパーサ、OAuth、tRPCを登録するが、CSP、frame-ancestors、HSTS、明示CORS、レート制限がない。 | CSP、クリックジャッキング防止、HSTS、MIME sniffing防止、許可Origin、リクエスト・招待・ログインのレート制限を設定して検証する。 |
| **P0** | 共有URLが機密リンクとして管理されていない | 現行共有は案件JSONをBase64化してURLハッシュへ入れる。暗号化・失効・期限・アクセスログはない。 | DB側のランダム共有トークンへ移行し、ハッシュ保存、期限、停止、再発行、アクセスログ、表示範囲を実装する。Base64は機密化ではない。 |
| **P0** | 公式の販売セキュリティ基準・例外承認がない | Agency OSの原本が未提示で、組織内のリリースゲートも未定義。 | 本資料の共通基準を採用するか、Agency OS／取引先基準へマッピングし、責任者が承認する。 |
| **P1** | セッションが長すぎ、重要操作の再認証がない | セッション有効期間は1年。メンバー招待、共有、削除などに再認証がない。 | 通常セッションと最大有効期間を短縮し、招待・権限変更・共有停止・削除・請求には再認証を要求する。 |
| **P1** | 招待トークンをDBへ平文保存し、期限がない | `project_members.inviteToken`は一意な文字列だが、ハッシュ化・期限・回数・レート制限がない。 | トークンはハッシュだけを保存し、短い期限、利用後失効、再発行、送信頻度制限を持たせる。 |
| **P1** | 組織単位のテナント分離が未実装 | 現行は案件所有者・メンバー単位。`organization_id`、組織管理者、行レベル分離はない。 | 販売版では認証済みセッションから組織文脈を決め、すべての取得・保存・キャッシュ・ストレージを組織で分離する。 |
| **P1** | 監査・監視・インシデント運用が不足 | 変更ログはあるが、認証失敗、権限拒否、共有アクセス、管理操作の監視・通知・保持方針がない。 | セキュリティログ、アラート、保持期間、調査手順、インシデント連絡責任者を定義する。 |
| **P1** | バックアップ、復旧、削除保持、データ所在地が未確認 | DBやホスティングの運用責任・RPO／RTO・復旧演習の証跡がない。 | バックアップ暗号化、復旧目標、復旧演習、削除・退会時のデータ処理、データ所在地を文書化する。 |
| **P2** | ストレージプロキシの公開範囲を運用前提にしている | `/manus-storage/*`はストレージの署名URLへリダイレクトする。利用者アップロード開始時の所有者検証は未実装。 | ユーザーファイルを始める前に、組織・案件プレフィックス、所有者検証、短期署名URL、内容タイプ検査、マルウェア対策を実装する。 |

OWASPは、認証済みセッションからテナント文脈を確定し、クライアントが送るテナントIDを信頼しないこと、データアクセス層でテナント分離を検証することを勧めている。[3] また、認証ではTLS、予測困難なセッション、認証失敗の記録、重要操作の再認証などを推奨している。[4]

## 5. 依存関係監査の結果

| 実行内容 | 結果 | 判断 |
|---|---|---|
| コマンド | `pnpm audit --prod --json` | 終了コード1。 |
| 対象 | 実行時依存関係547件 | 開発依存は含めない。 |
| 検出数 | 高17件、中47件、低8件、重大0件 | **販売向けリリースゲートを不合格**とする。 |
| 例 | `path-to-regexp`、`lodash`／`lodash-es`、`nanoid`、`DOMPurify`、`mermaid`、`axios`系の依存連鎖 | 利用到達性を個別確認しても、高・中を放置したまま販売しない。 |

監査結果には、現行画面で直接使っていない可能性がある依存関係も含まれる。そのため、個別の到達性と更新可否を確認する必要はある。ただし、これは販売前の除外理由ではない。依存関係の棚卸し、不要な依存の削除、修正版への更新、再監査を先に行う。

## 6. 販売可否の段階判定

| 段階 | 判定 | 条件 |
|---|---|---|
| サンプル・社内開発 | 条件付き可 | 実データを入れず、アクセスを限定し、既知の制限を利用者へ説明する。 |
| 少人数の実案件パイロット | **P0対応後に可** | 依存関係、CSRF、ヘッダー、レート制限、共有URLの扱いを改修し、管理者・編集者・閲覧者で実操作を確認する。 |
| 販売・全社展開 | **HOLD** | P0・P1対応、第三者または独立者によるセキュリティレビュー、バックアップ・監視・事故対応・顧客向け説明の整備を完了する。 |

## 7. Agency OSへ再照合する手順

Agency OSの原本を受領したら、以下の形式で再評価する。

| Agency OS要件ID | 要件 | 現行証跡 | 判定 | 不足時の対応 | 責任者・期限 |
|---|---|---|---|---|---|
| 例：AO-IAM-01 | 管理者の強い認証 | OAuthと再認証の実装・テスト | PASS／HOLD | MFAまたは再認証を実装 | セキュリティ責任者／日付 |

判定は `PASS`、`HOLD`、`対象外` の三つだけにする。要件原本がない項目は推測でPASSにしない。

## 8. 次に行うべき順序

1. **依存関係の修正**：不要なライブラリを外し、残る実行時依存を更新し、監査で高・中を0件にする。
2. **共有の再設計**：Base64の共有URLを停止し、失効・期限・ログを持つサーバー側共有トークンへ移す。
3. **HTTPとCSRFの保護**：CSP、HSTS、frame-ancestors、Origin検証／CSRF、レート制限、本文サイズの見直しを実装する。
4. **販売版の組織分離**：組織、組織管理者、`organization_id`、テナントスコープのデータアクセスを実装する。
5. **運用証跡**：監査ログ、脆弱性対応SLA、バックアップ復旧、インシデント対応、顧客向けセキュリティ説明を整える。
