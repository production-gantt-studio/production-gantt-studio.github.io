## 3. なぜ遅れたか

### 3.1 前提を状態として固定しなかった

利用者が「Supabaseにはログイン済み」と伝えた後も、自動操作用ブラウザが未ログインだったことを、新たな確認事項として利用者へ戻した。本来は次のように分けるべきだった。

| 状態 | 正しい扱い |
|---|---|
| 利用者Chromeはログイン済み | 以後、利用者へログインを聞かない固定事実。 |
| 自動操作ブラウザはCookie未同期 | AI側の制約。直接管理接続、または一度だけ必要な端末認証へ切り替える。 |
| 旧Manus版が開いている | テストを中止し、独立版URLへAI側で切り替える。利用者にURL探索を頼まない。 |

### 3.2 受入条件より調査を優先した

「メールが届かない」「既存案件移行に失敗した」「Passkey登録で500になる」という不具合ごとに、調査、文書化、別案の提案を挟んだ。必要なのは、問題を見つけた時点で**修正 → テスト → 本番反映 → 同じ画面で再テスト**までを一つの単位として終えることだった。

### 3.3 部分成功を完成扱いに近づけた

編集者招待リンクの認証を本番で通せても、管理者が翌日に入り直せなければツールは実務で止まる。技術的な部分テストは完了条件ではない。完成判定は、管理者の実務フローが途切れず通るかだけで行う。

### 3.4 認証方式の変更を、実証より先に積み上げた

通常メール未達の対策として、一時ログインリンク、招待認証、Passkeyを順に追加した。機能を足す前に、既存方式を捨てるか、使える復旧経路を1本に絞るべきだった。認証は「複数の代替案」ではなく「翌日も使える1本の入口」を完成させる。

## 4. Claudeが守る実装ルール

### 4.1 完成の定義をコード前に固定する

実装開始前に、次の表を作り、全行が実測でPASSになるまで「完成」「出荷」「運用可能」と書かない。

| 受入項目 | PASSの証拠 |
|---|---|
| 管理者の再ログイン | ブラウザを閉じる、またはログアウトした後、通常運用の入口から本人が再ログインできる。 |
| 案件作成・保存 | 管理者がSampleではない検証案件を作成し、再読み込み後も残る。 |
| 編集者招待 | 管理者または編集者が招待リンクを発行し、別編集者がリンクだけでログイン・受諾できる。 |
| 権限 | 編集者は新規案件ボタンを見ず、既存案件を編集できる。 |
| 共有 | 未ログインのURLで対象案件だけが見え、取消後に読めない。 |
| アーカイブ | 検証案件を30日アーカイブし、復元後の保存状態を確認してから再アーカイブする。 |

### 4.2 作業を「修正単位」で終える

不具合を見つけたら、次の順だけで進める。途中で長い進捗報告、別方式の比較、追加の設計文書を作らない。

1. 失敗画面またはログから原因を1つに絞る。
2. 影響範囲を既存コード・テストで確認する。
3. 最小変更を実装する。
4. 型検査、回帰テスト、本番ビルドを1回実行する。
5. GitHub mainと本番へ反映する。
6. **同じ失敗画面・同じ操作で再テストする。**
7. PASSなら次の不具合へ進む。FAILなら同じ原因を再調査し、利用者には聞かない。

### 4.3 状態台帳を1行で維持する

会話中に一度確定した事実は、次の形式で状態台帳へ書く。後の処理は台帳を読む。利用者へ同じことを聞き直さない。

```text

独立版URL: https://rikufujita1229-sudo.github.io/production-gantt-studio/
旧Manus URL: テスト・運用対象外
通常メール: 受信未達のため通常ログイン入口として使わない
編集者招待: 一回限り認証付きリンクで本番受諾済み
管理者再ログイン: Passkey登録・再ログインがPASSするまで未完了
```

### 4.4 利用者へ頼めるのは物理的に代行できない1操作だけ

Touch ID、端末PIN、Passkeyの生体認証、本人しか開けない受信箱はAIが代行できない。それ以外のURL移動、画面切替、コード反映、DB反映、テストデータ整理、ログ確認はClaude側で行う。

依頼時は、以下の条件をすべて満たすこと。

| 禁止 | 許可される依頼 |
|---|---|
| URL入力、画面探索、複数候補の選択、設定用語の説明、スクリーンショット要求 | 「いま開いている画面の『この端末に登録』を1回押し、Touch IDまたは端末PINを通してください」の1操作だけ。 |

### 4.5 中間報告は止める理由にしない

進捗報告が必要な場合も、修正・テスト・公開を止めずに一文で書く。報告だけで待機状態にしない。止めてよいのは、費用発生、破壊的操作、本人認証、生体認証、公開投稿など、本人の意思が必要な操作だけである。
